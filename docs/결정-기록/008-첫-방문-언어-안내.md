# ADR-008: 첫 방문의 루트 주소만 브라우저 언어 판으로 안내

- 상태: 채택 (2026-10-05)
- 결정자: 운영자

## 맥락

언어는 경로로 나뉘어 있어(ADR-005) 검색 유입은 hreflang으로 이미 각자의 언어 판에 떨어진다. 하지만 주소를 직접 치거나 링크로 `getqrmaker.com`에 처음 오는 방문자는 무조건 영어를 보게 된다. 한국어 브라우저로 들어온 사람이 영어 화면에서 언어 메뉴를 찾아야 하는 것은 불필요한 이탈 요인이다. 반대로 Accept-Language로 모든 페이지를 바꾸면 검색엔진 색인과 hreflang이 깨진다.

## 결정

- `proxy.ts`가 **루트(`/`)에 대한 GET 요청만** 본다. `qr_lang` 쿠키가 있으면 그 판으로, 없으면 Accept-Language(q값·지역 태그를 해석하는 `preferredLocale`)에서 지원 언어를 고른다. 영어면 그대로, 아니면 `/<코드>`로 302.
- 쿠키는 1년. 사이트 안에서의 이동(Referer가 같은 호스트 — 언어 메뉴·푸터 언어 행)은 절대 되돌리지 않고, 그때 도착한 판을 쿠키에 기억한다. 그래서 한국어 브라우저라도 "English"를 고르면 이후 직접 방문도 영어다.
  - "같은 호스트"는 방문자가 쓴 Host(또는 X-Forwarded-Host) 헤더와 비교한다. 컨테이너 안의 `req.nextUrl.host`는 내부 주소(app:3000)라 공개 도메인 Referer와 절대 맞지 않아, 운영에서 언어 메뉴의 영어 선택이 다시 /ko로 튕기던 원인이었다(2026-10-06 수정). 로컬 E2E는 두 값이 같아 잡지 못한다.
- 크롤러·헤드리스·Lighthouse(UA 패턴)는 항상 영어 루트를 받는다. 응답에는 `Vary: Accept-Language, Cookie`.
- 깊은 링크(`/wifi-qr-code` 등)는 손대지 않는다.

## 결과

- 긍정: 브랜드 직접 유입이 자기 언어로 시작한다. IP 기반이 아니라 해외 거주자·여행자도 브라우저 언어대로 보인다. 외부 서비스(Cloudflare 등) 의존 없음.
- 부정/트레이드오프: 루트의 첫 응답이 302 한 번 추가된다. 언어 감지 테스트는 Playwright에서 `extraHTTPHeaders`가 아니라 컨텍스트 `locale`로 해야 한다(브라우저가 Accept-Language를 덮어씀).
- 검증: 단위 테스트 4건(파서), E2E 4건(한국어 브라우저 → `/ko`, 영어 그대로, 언어 메뉴 선택 유지, 크롤러 제외).
