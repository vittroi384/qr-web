# ADR-004: 민감값은 저장 전 양쪽에서 마스킹한다

- 상태: 채택 (2026-10-02) — 초기의 "설정으로 끌 수 있는 마스킹"은 리뷰 지적으로 폐기
- 결정자: 운영자

## 맥락

Wi-Fi QR은 비밀번호를 평문으로 담는다. 운영자가 방문자 입력을 기록하므로 비밀번호가 DB·CSV·감사 로그에 남을 위험이 있다. 1차 구현은 관리자 설정 `mask_wifi_password`로 마스킹을 끌 수 있었고, 길이 기반 마스킹(`********`)이 비밀번호 길이를 노출했다.

## 결정

- 클라이언트는 전송 전에 `password`를 `****`로, 인코딩 문자열의 `P:…;`를 `P:****;`로 바꾼다.
- 서버는 받은 값과 무관하게 저장 직전에 다시 고정 `****`로 덮어쓴다(`hardenSecretsForStorage`). 텍스트 타입에 `WIFI:` 문자열을 붙여 넣은 경우도 같은 규칙을 적용한다.
- 자르기(200자) 전에 마스킹해 잘린 꼬리에 비밀번호 조각이 남지 않게 한다.
- 이 동작을 끄는 설정은 두지 않는다.

## 결과

- DB·CSV 어디에도 비밀번호 원문과 길이가 남지 않는다(리뷰에서 DB 전수 확인).
- 운영자도 방문자의 Wi-Fi 비밀번호를 볼 수 없다. 이는 의도된 제약이다.
- 다른 민감 타입(암호화폐 주소 등)은 공개 정보로 보고 마스킹하지 않는다. → **2026-10-06에 아래로 확장.**

## 확장 (2026-10-06): 연락처·본문도 일부만 남긴다

공개 후 보안 점검에서 "Wi-Fi 비밀번호와 은행 식별자 외에는 전화·이메일·메시지 본문·좌표·지갑 주소가 평문으로 남는다"는 지적을 받았다. 운영자가 보고 싶은 것은 "어떤 종류의 QR이, 어느 도메인·플랫폼으로 만들어지는가"이고 연락처 원문은 필요하지 않다고 판단해, 서버 저장 직전(`hardenSecretsForStorage`)에 다음을 추가했다.

- 전화(whatsapp·sms·phone·vcard): 앞 3자리·뒤 4자리만 남김 (`010-****-5678`). 이메일(email.to·vcard.email): 앞 2자 + `****` + 도메인.
- 지갑 주소(crypto.address)·결제 핸들(payment.handle): 앞뒤 4자.
- 본문·메모(text.text, email.subject/body, sms·whatsapp.message, event.description, vcard.note/address, pix.description, upi.note, epc.remittance/info, crypto.label): 앞 40자 + `… (n자)`.
- 좌표(geo.lat/lng): 소수 2자리(약 1km).
- URL·SNS 핸들·종류·이름·금액은 그대로 둬 관리자 분류(도메인·플랫폼)와 요약은 유지된다.
- 마스킹된 필드가 인코딩 문자열에 그대로 들어가는 종류(sms·vcard·email 등)는 `encoded_preview`를 저장하지 않는다. 미리보기는 관리자 텍스트 검색에만 쓰여 손실이 작다.

여전히 이 동작을 끄는 설정은 없다. 클라이언트는 바꾸지 않았다(원문은 저장 요청 한 번에만 서버로 가고, 서버가 저장 직전에 가린다).
